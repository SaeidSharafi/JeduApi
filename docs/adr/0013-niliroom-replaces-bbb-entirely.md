# Niliroom replaces BBB entirely; the BBB delivery path is retired

ADR 0007 chose Niliroom as the primary panel for `live_session_bbb` seminars but kept a legacy `BbbService` fallback for when Niliroom was disabled or unconfigured, and ADR 0012 retired only BBB's *admin settings surface* while keeping `BbbService`, `config/services.bbb`, `SettingKeyEnum::BIG_BLUE_BUTTON` and `ProvisioningProviderEnum::BBB` alive as an environment-configured fallback.

We have changed that: the fallback is gone. Niliroom is the only provider for `live_session_bbb`, and the BBB integration is retired outright.

Two reasons. First, a fallback that ADR 0012 removed from the admin panel can only be configured by deployment environment, so it is a code path nobody exercises, nobody can tune from the product, and nobody would notice rotting — it is configuration debt that only pays out on the day the primary provider is already broken. Second, keeping BBB alive means keeping two provider adapters, two settings keys, two provisioning providers and two join flows correct for one delivery method, which is the opposite of what the delivery method needed.

`live_session_bbb` **stays** as the persisted `delivery_method` value and as a public API value: it names how the product is delivered (a live session), not which vendor runs it. The vendor behind it is Niliroom only. When the Niliroom panel is disabled or unconfigured, the teacher and student login flows return a clear error and an operator fixes the provider settings; they do not silently degrade to another provider.

Removal (#113) covers `BbbService`, `BbbClientContract`, `FakeBbbService`, `BbbProvisioningProvider`, `ProvisioningProviderEnum::BBB`, `SettingKeyEnum::BIG_BLUE_BUTTON`, `config/services.bbb`, the seeder row, and every branch that dispatches or whitelists `bbb` — including the retry endpoint's provider whitelist and `ProvisioningPlanResolver`. There is **no data migration and no compatibility layer**: existing rows that reference `bbb` (settings rows, provisioning attempts, `meeting_id` details, seeded order fixtures) are abandoned, and staff re-point seminars at a Niliroom room. Translating them would mean writing a migration for a provider we are deleting, to feed a mapping we are deleting with it.

Ordering is a hard constraint, not a preference: teachers must reach Niliroom first (#55) and students must too (#112) before BBB can be removed (#113). ADR 0012 named exactly this — "retiring the BBB delivery path itself is a separate decision that cannot be taken before the Niliroom adapter ships, because a `live_session_bbb` seminar would otherwise have no join URL at all". The adapter shipped (#54); this ADR takes the decision; #112 and #113 execute it.

**`live_session_bbb` gets no Niliroom provisioning provider.** `BbbProvisioningProvider` exists only to copy a staff-entered meeting id out of `details_json` into the enrollment's provisioning data — there is no remote resource to create, because rooms are staff-created and Niliroom participants are enrolled at join time. Niliroom is therefore a live-session adapter, not a `ProvisioningProviderEnum` case: after #113 removes the BBB case, `live_session_bbb` plans zero providers and the join flows read `nili_room_id` from the delivery option directly (`ProvisioningRegistry` has nothing to resolve for it). Adding a Niliroom adapter to the provisioning registry would invent a resource lifecycle the panel does not have.

Consequences: `NiliroomService` and `NiliroomClientContract` are the only live-session adapter, its settings record becomes load-bearing rather than stageable (ADR 0012's status note), and `ProvisioningProviderSettingsEnum::NILIROOM::serviceClass()` names the adapter so the admin panel's readiness badge is the same value the flows gate on — the login flows check `isReady()` themselves, because `assertConfigured()` covers configuration only, not the `enabled` switch. The one open design question this ADR does not answer is which Niliroom grant a *student* receives — panel login grant or meeting join grant — which is recorded as the first task of #112 and must be settled there before BBB is removed.

**Supersedes:** ADR 0007's "BBB fallback" bullet and ADR 0012's paragraph keeping `BbbService` alive as an environment-configured fallback.
