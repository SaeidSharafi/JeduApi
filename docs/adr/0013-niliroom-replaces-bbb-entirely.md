# Niliroom replaces BBB entirely; the BBB delivery path is retired

ADR 0007 chose Niliroom as the primary panel for `live_session_bbb` seminars but kept a legacy `BbbService` fallback for when Niliroom was disabled or unconfigured, and ADR 0012 retired only BBB's *admin settings surface* while keeping `BbbService`, `config/services.bbb`, `SettingKeyEnum::BIG_BLUE_BUTTON` and `ProvisioningProviderEnum::BBB` alive as an environment-configured fallback.

We have changed that: the fallback is gone. Niliroom is the only provider for `live_session_bbb`, and the BBB integration is retired outright.

Two reasons. First, a fallback that ADR 0012 removed from the admin panel can only be configured by deployment environment, so it is a code path nobody exercises, nobody can tune from the product, and nobody would notice rotting — it is configuration debt that only pays out on the day the primary provider is already broken. Second, keeping BBB alive means keeping two provider adapters, two settings keys, two provisioning providers and two join flows correct for one delivery method, which is the opposite of what the delivery method needed.

`live_session_bbb` **stays** as the persisted `delivery_method` value and as a public API value: it names how the product is delivered (a live session), not which vendor runs it. The vendor behind it is Niliroom only. When the Niliroom panel is disabled or unconfigured, the teacher and student login flows return a clear error and an operator fixes the provider settings; they do not silently degrade to another provider.

Removal (#113) covers `BbbService`, `BbbClientContract`, `FakeBbbService`, `BbbProvisioningProvider`, `ProvisioningProviderEnum::BBB`, `SettingKeyEnum::BIG_BLUE_BUTTON`, `config/services.bbb`, the seeder row, and every branch that dispatches or whitelists `bbb` — including the retry endpoint's provider whitelist and `ProvisioningPlanResolver`. There is **no data migration and no compatibility layer**: existing rows that reference `bbb` (settings rows, provisioning attempts, `meeting_id` details, seeded order fixtures) are abandoned, and staff re-point seminars at a Niliroom room. Translating them would mean writing a migration for a provider we are deleting, to feed a mapping we are deleting with it.

Ordering is a hard constraint, not a preference: teachers must reach Niliroom first (#55) and students must too (#112) before BBB can be removed (#113). ADR 0012 named exactly this — "retiring the BBB delivery path itself is a separate decision that cannot be taken before the Niliroom adapter ships, because a `live_session_bbb` seminar would otherwise have no join URL at all". The adapter shipped (#54); this ADR takes the decision; #112 and #113 execute it.

**`live_session_bbb` gets no Niliroom provisioning provider.** `BbbProvisioningProvider` exists only to copy a staff-entered meeting id out of `details_json` into the enrollment's provisioning data — there is no remote resource to create, because rooms are staff-created and Niliroom participants are enrolled at join time. Niliroom is therefore a live-session adapter, not a `ProvisioningProviderEnum` case: after #113 removes the BBB case, `live_session_bbb` plans zero providers and the join flows read `nili_room_id` from the delivery option directly (`ProvisioningRegistry` has nothing to resolve for it). Adding a Niliroom adapter to the provisioning registry would invent a resource lifecycle the panel does not have.

Consequences: `NiliroomService` and `NiliroomClientContract` are the only live-session adapter, its settings record becomes load-bearing rather than stageable (ADR 0012's status note), and `ProvisioningProviderSettingsEnum::NILIROOM::serviceClass()` names the adapter so the admin panel's readiness badge is the same value the flows gate on — the login flows check `isReady()` themselves, because `assertConfigured()` covers configuration only, not the `enabled` switch.

**Students get the meeting join grant, and the panel owns the meeting lifecycle (#112).** The two Niliroom grants are not interchangeable: `POST /login-grants` authenticates into the panel, which is teacher access, while `POST /meetings/{meeting}/join-grants` joins a live meeting, which is what a student attends. A student therefore gets a meeting join grant, addressed to their enrolled `student` identity (`{user_id}`, never the `guest` alternative, which would mint a participant outside the room roster), and never lands in the panel UI. A meeting join grant carries no lifetime, so the student response's `expires_at` is null — unlike the teacher's login grant, whose expiry is the panel's own.

The platform stores **only `nili_room_id`** on the delivery option: there is no staff-entered meeting ID, no `nili_meeting_id` detail, and no platform-side record of which session is live. A meeting is addressed only by the panel's own public ID, obtained at request time, which is why nothing about a meeting can go stale here.

**The panel starts the meeting; the platform asks for it.** A student's join request calls `POST /rooms/{room}/meetings/start` before issuing the grant. That call is start-or-get on the panel's side: with a meeting already running it returns that meeting, and with nothing running it starts one. So a session that an operator or teacher has already opened costs a student nothing extra, and a student who clicks Join before anyone opened the room gets a working join URL into a freshly started meeting rather than an error — there is no "no live session" state for this platform to render, and no local gate to keep in sync. The consequence is that a student's click can start a session; the panel remains the only thing that decides whether a meeting runs, and the platform never creates, ends or tracks one. This also means the student join carries no provisioning gate: `live_session_bbb` is served from the delivery option's room ID, not from an enrollment's provisioning state, which after #113 is empty for this method anyway.

The enrollment upsert is authoritative on every join: the platform re-asserts the shop user's `student` role in the room, which is what makes a revoked or time-boxed panel-side enrollment come back for a student who is still entitled in the shop. The shop holds the entitlement; the panel holds the meeting. Teacher and student flows share one provider identity per shop user, so the same person is one Niliroom user with a single role per room — a staff member who is also enrolled as a student in the same room ends up with whichever role was asserted last.

**Supersedes:** ADR 0007's "BBB fallback" bullet and ADR 0012's paragraph keeping `BbbService` alive as an environment-configured fallback; ADR 0012's consequence that `BbbService`'s `default_attendee_pw` / `default_moderator_pw` read "must still be corrected, since the student join path depends on those passwords"; and ADR 0007's consequence that `BbbService` gains a role-based join for the student path.
