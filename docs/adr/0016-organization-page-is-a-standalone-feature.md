# The Organization page is a standalone landing-page feature

The Organization page is implemented as its own one-off feature, with public and administrative routes grouped around that feature and a required link to one Vendor for department-owned recent courses. Its recent-course query is rooted in Course records associated with any Course Product belonging to that Vendor, defaults to six records, and accepts an optional limit capped at twenty. Eligibility filters are applied only when loading an optional Product shell for price and commercial delivery data; a Course remains in the recent list when no eligible Product resolves, so the flat `ProductCardData` can show the Course identity without commercial fields. Course supplies the catalog identity and presentation fields, while an available Product overlays commerce fields; no nested course/product objects are exposed. It is persisted as a dedicated singleton record rather than a generic settings row. The record owns Organization-specific informational content, FAQ data, and the external IMS portal reference; FAQ items are ordered JSON objects with `question`, `answer`, and `is_visible`. The admin side uses its existing Mediable relation for page media, so media is not represented by a dedicated `hero_image_id` field. The update action denormalizes the public `hero` and `educational_calendar` media URLs into `hero_image_url` and `educational_calendar_url`; the shop endpoint reads those columns and does not load the media relation. Its public projection is cached per requested recent-course limit and invalidated when the page or linked Vendor is updated. The shop projection does not expose the internal numeric Vendor ID; because the current Vendor schema has no slug or UUID, it returns the department name only. The existing dedicated partners link remains canonical and partner data is not duplicated in this page record. The page contract permits optional content and external references to be absent. It is not a generic Vendor landing-page template: future pages such as English learning or children’s education may have their own fields, routes, design, and behavior unless real reuse emerges.

The singleton is enforced with a unique database sentinel fixed at 1, and application reads use that fixed row rather than an unconstrained first row. The cached shop projection is invalidated after both Organization page updates and Vendor updates, so linked department changes are reflected immediately.

## Considered Options

A shared Vendor landing-page type was rejected because each planned page is a single, independently designed experience; a generic contract would force unrelated requirements into one nullable model and API.
