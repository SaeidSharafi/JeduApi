# One cache gateway with an explicit key registry and explicit invalidation

Caching in this codebase grew into three overlapping mechanisms with no shared vocabulary: the Laravel `Cache` facade, the `SmartCache` package facade (`iazaran/smart-cache`), and a model-observer + config-map combo (`app/Observers/InvalidationObserver.php` + `config/cache_invalidation.php`) that clears caches invisibly. Cache keys are string literals scattered across services, models and controllers; group invalidation goes through `SmartCache::flushPatterns()`, which reads a hidden global key index (`_sc_managed_keys`); and the "SWR" wrapper (`app/Services/SWRCacheService.php`) actually refreshes **synchronously inside the request** while its docblock claims a background refresh. A read-only audit (see `CACHE_AUDIT_REPORT.md`) found invalidations missing on several write paths, including a staff-permission list cached forever with no invalidator and a 6-minute authentication window after bulk token revocation.

We decided to consolidate on **one cache engine, one key registry, one invalidation vocabulary, and one entry point**, with invalidation declared explicitly at each write site:

1. **One engine — Laravel's cache only.** `Cache::flexible()` (native SWR, deferred after the response) and `Cache::lock()` (native locks) replace `SmartCache::swr()`, `SmartCache::lock()`, and `flushPatterns()`. The `iazaran/smart-cache` dependency is removed; its compression/chunking strategies are unused here and its key index is precisely the hidden machinery we are removing.
2. **One key registry — `CacheKey` enum.** Every key template, its `ttl()`, its `staleTtl()`, and its invalidation group live in one enum. No cache-key string literal exists outside it (`'search:'`, `'otp_'`, `'AccessToken::'`, `'digipay_access_token'`, `'student_quizzes:'`, `'discounts.handler_registry.cache'`, `'database.pgroonga_enabled'` all move in). `CacheKeysEnum` is folded into it.
3. **One invalidation vocabulary — `CacheTag` enum** (`HomePage`, `Content`, `Catalog`, `Search`, `Discounts`, `Settings`, `Auth`). Each `CacheKey` declares exactly one group; a write path names the groups it disturbed. "What invalidates what" is declared once, on the key, instead of in an observer plus a config map plus ad-hoc `forget()` calls.
4. **One entry point — `CacheStore` interface with one implementation.** `LaravelCacheStore` is the only class permitted to import the cache facade; it owns key resolution, durations and group invalidation. Locks are deliberately **not** wrapped: call sites use Laravel's `Cache::lock()` directly. A second interface whose only job is to supply a default argument inverts nothing and adds a class, a binding and a test double for one implementation, and Laravel's locking is already an abstraction (`Illuminate\Contracts\Cache\LockProvider`). `AppServiceProvider` binds the gateway.
5. **Explicit invalidation, no hidden clearing.** `InvalidationObserver`, `SettingObserver` and `config/cache_invalidation.php` are deleted. A mutating action or job calls `$this->cache->invalidate(CacheTag::X, ...)` in plain sight, after the transaction commits. Per-user keys are cleared precisely with `forget(CacheKey::Y, ['id' => $id])` — for example, bulk token revocation iterates the deleted tokens and forgets each `AccessToken::{hash}` and `Tokenable` entry, which is impossible to get right through a model observer.
6. **Group invalidation by version counters, not tags.** Each `CacheTag` has one counter key (`cache.version:{tag}`); `invalidate()` bumps it atomically, and `CacheKey` resolution prefixes the resolved key with the group's current version. Old entries become unreachable and expire by TTL. This is chosen over native `Cache::tags()` because tags require a taggable store (`DatabaseStore` is not taggable — `vendor/laravel/framework/src/Illuminate/Cache/DatabaseStore.php:18`), and the repository must keep working on the `database` driver, which `config/cache.php` defaults to and `.env.testing` uses. The Pest suite runs on `array` and production on Redis, so a driver-specific mechanism would make test and production behaviour diverge. Version counters give identical semantics everywhere in one transparent implementation, and both `increment()` paths handle a missing counter on Redis and database.
7. **Refresh by after-response deferral only.** `CacheStore::flexible()` wraps `Cache::flexible()` and always passes an explicit single-flight lock, so callers cannot forget it. Refresh runs after the response is flushed, in the same worker, with no queue and no hidden job dispatch. Queue-backed SWR is deliberately not adopted.

**Why the explicit route over observers.** A missed invalidation must be visible in a diff, not hidden in an event dispatch. The accepted cost is that dropping the observer removes the safety net: a forgotten `invalidate()` is now a real bug in an action. That is mitigated by enforcement rather than by magic — a Pest architecture test fails if ad-hoc cache **storage** access (`Cache::`, `cache(` or `SmartCache::`) appears outside the cache module, with `Cache::lock()` explicitly allowed because locks are coordination rather than storage — and a per-tag coverage test asserts every `CacheTag` is invalidated by at least one writer.

## Considered Options

- **Unify on `SmartCache` instead of Laravel.** Rejected: pattern invalidation is implemented by scanning a package-maintained key index (`_sc_managed_keys`), which is the debuggability problem itself, and the package's unique value (compression, chunking, queue-backed refresh) is unused by this application.
- **Laravel cache tags for group invalidation.** Rejected because `DatabaseStore` is not taggable and the repository still supports that driver; forcing Redis everywhere to buy tags is a larger constraint than the ten-line version counter it replaces. The choice is isolated behind `CacheStore`, so switching to tags later touches one class.
- **Keep the observer + config map as the invalidation mechanism.** Rejected: hidden clearing is what made the missing invalidations hard to see, and it cannot express per-user keys or mass-delete paths such as `$user->tokens()->delete()`.
- **Queue-backed SWR (`SmartCache::asyncSwr` / `refreshAsync`).** Rejected: it is a second refresh mechanism requiring serializable callbacks, and the latency goal is already met by `Cache::flexible()`'s after-response deferral. It would also reintroduce exactly the "hidden dispatch" the audit objected to.
- **Wrap `Cache::flexible()` per call site instead of in the gateway.** Rejected: callers would silently omit the single-flight lock, which collapses to a 1-second TTL when unset (`vendor/laravel/framework/src/Illuminate/Cache/RedisStore.php:186-193`).
- **A second interface for locks (`CacheLockStore`).** Rejected: one implementation, no behaviour beyond defaulting `seconds`/`wait`, and a framework abstraction already exists. It would invert nothing while adding a class, a binding and a double. The one lock guarantee that matters — single-flight refresh — lives inside `CacheStore::flexible()` and is unaffected.

## Consequences

- `Cache::flexible()` refreshes after the response in the same PHP-FPM worker, not on a queue. If the worker dies mid-refresh the refresh is lost; the next request retries because the fresh-TTL check still fails. This is acceptable for the cached payloads here (settings, homepage content, search results) and removes a queue dependency from the read path.
- **Never cache `null`.** `Cache::flexible()` cannot distinguish a stored `null` from a miss and will re-run the callback on every request. All values cached through the gateway are collections, arrays or DTOs.
- `forget()` deletes the value and leaves `illuminate:cache:flexible:created:{key}` to expire; a missing value already forces regeneration on the next read, so no internal framework key is manipulated.
- Version bumps orphan the previous generation of keys until their TTL expires. Peak Redis usage is bounded by one extra generation per group, which the existing TTLs (300–3600s, plus `staleTtl`) keep small.
- Removed: `iazaran/smart-cache`, `app/Services/SWRCacheService.php`, `app/Services/CacheInvalidationService.php`, `app/Observers/InvalidationObserver.php`, `app/Observers/SettingObserver.php`, `config/cache_invalidation.php`, `app/Enums/System/CacheKeysEnum.php`, and the dead, fatally broken `app/Jobs/Discounts/RegenerateAllDiscountPricesJob.php` (it called `->key()` on array-valued config entries).
- Kept and retargeted to the gateway: `discounts:clear-cache` (`CacheKey::DiscountHandlers`) remains the manual escape hatch for handler discovery; `RequestDataCacheService` stays but is a per-request memo, not a cache.
- Added, following the repository's existing placement conventions rather than nesting one module folder: the `CacheStore` gateway interface under `app/Contracts/Cache/` (matching `app/Contracts/Payment/`, `app/Contracts/Integrations/`; locks are not abstracted), enums under `app/Enums/System/` (alongside the `CacheKeysEnum` they replace), the `LaravelCacheStore` implementation under `app/Services/Cache/`, and the container binding in `AppServiceProvider` beside the existing interface-to-service binds. Plus `php artisan cache:keys|cache:invalidate|cache:versions` and the architecture test.
- `products.price_data_cache` is a persisted projection rather than a cache; it stays as is, but its name is misleading and a rename (`price_snapshot`) is a separate, out-of-scope change.
- `deploy.php` keeps running `artisan:cache:clear`, which now also resets the version counters — acceptable because it runs before `permissions:sync`.

## Testing approach

Tests follow the repository testing rules and the framework's own defaults. Laravel already runs the suite on the `array` cache driver, so the gateway's contract tests drive the real `LaravelCacheStore` over the array store — no database, no HTTP, no mock — and that is where key resolution, durations, version-counter invalidation and the null sentinel are pinned. Invalidation is asserted by effect: warm an entry, perform the write, assert the next read regenerates. An interaction assertion would still pass with a wrong resolved key, and it suppresses the mutants it was meant to catch.

Behaviour verification is reserved for the one thing state cannot show — whether a read was a cache hit or a miss. Fowler's classical standard makes the same exception: "you can't tell from its state whether the cache hit or missed … behavior verification would be the wise choice for even a hard core classical TDDer."

Everywhere else: fakes before mocks, and the real implementation over both. Never mock Eloquent models, the query builder or the test database — create real records with factories. Mock only across a process boundary (outbound HTTP, provider and payment clients), where the real implementation leaves the process or is nondeterministic.

## Migration plan

Each phase leaves the test suite green.

1. **Introduce the gateway (no behavior change).** Add `CacheKey`, `CacheTag`, `CacheStore` + `LaravelCacheStore`, and the container binding. Nothing consumes them yet except tests.
2. **Port call sites.** Move every cache read/write to the gateway: settings, sliders, partners, student stories, good-for-start, search + suggestions, quizzes, OTP, Digipay token, access tokens, handler registry, PGroonga. Replace the SWR wrapper with `CacheStore::flexible()`, and replace `SmartCache::lock()` with Laravel's `Cache::lock()` at the call sites.
3. **Replace hidden invalidation with explicit calls.** Add `invalidate()`/`forget()` calls to the write paths identified in the audit (staff permissions, bulk token revocation, settings→Digipay token, course/category→student stories, search index sync → `CacheTag::Search`, discount reindex and status toggle → `Catalog`/`Search`/`Discounts`, quiz submission → per-user key). Then delete `InvalidationObserver`, `SettingObserver` and `config/cache_invalidation.php`.
4. **Remove the old engine.** Delete `SWRCacheService`, `CacheInvalidationService`, `CacheKeysEnum`, the dead discount job, and `composer remove iazaran/smart-cache`.
5. **Enforce and document.** Add the architecture test, the per-tag coverage test, the three artisan commands, and update the Digestion docs for any changed service/interface listings.
